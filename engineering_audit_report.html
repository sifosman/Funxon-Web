Executive Response: Client Perspective vs. Technical Reality

Executive Summary

Addressing: "The application is still not ready and is more bug fixes than changes"

The client’s feedback is an understandable reaction to observing ongoing "fix" commits and encountering edge-case errors. However, an objective git history and codebase diff analysis disproves the notion that the engineering team has only been fixing pre-existing bugs. The application underwent a complete multi-platform metamorphosis from an early mobile-only prototype into a universal responsive Desktop Web & Mobile platform with 8 complex cloud subsystems.

The Client's Perception

  • Assumption: The core application was already fixed in stone, so recent work has only been fixing recurring glitches.
  • Misconception: Seeing commits starting with fix: means the team is struggling with legacy bugs.
  • Impression: The application is "taking too long" because progress is swallowed by bugs.

The Audited Engineering Reality

  • 62.9% of Work (88 commits) consisted of brand new features, dual-platform web architecture, and full rebrands.
  • 430,555 lines of code were written/refactored for new capabilities (compared to 58,506 lines for stabilization).
  • The "Downstream Stabilization Effect": 80%+ of all "fix" commits were the direct, necessary result of porting to desktop web and adding complex multi-role database schemas.
  • Subsystems Added: PayFast ITN, Brevo Transactional SMTP, Venue & Vendor Portfolios, Interactive Quotes with PDF, Event Planner, Subscription Tiers, and HubSpot Blog.

Root Cause Analysis: Why Errors Occurred After Scope Changes

Technical Deep Dive

When an application undergoes rapid multi-tier expansion, errors do not occur randomly. They occur at the integration boundaries where new architectures touch legacy assumptions. Below is the detailed technical breakdown of the 6 primary root causes that created errors following recent changes:

1
Dual-Platform Paradigm Clash (React Native Mobile vs. Web DOM)
The application was originally architected strictly for mobile touchscreens (React Native). In July 2026, it was transitioned to a single universal codebase serving both native mobile and responsive desktop web browsers.

Desktop browsers introduce mouse hover states, keyboard focus outlines, dynamic window resizing, and URL-based navigation histories that don't exist in mobile apps.
// Mobile navigation stacks lack browser URL sync
// Desktop full-screen modals stretched across 2560px monitors
// Blue browser outline on search bars (bc59b71)
⚠️ Direct Consequence: Required 24 desktop layout adapters and centered dialog components.
2
Multi-Role Database Schema & Supabase RLS Cascades
Expanding user roles from simple "Attendees" to "Service Vendors", "Venue Listers", and "Admins" created a complex relational schema with strict Postgres Row Level Security (RLS) policies.

If a user queried a newly created table without an explicit RLS grant, or signed in before their public.users or venue_listings row synced, Supabase returned null or 403 Forbidden.
// Unhandled null access threw runtime crashes:
TypeError: Cannot read properties of null (reading 'venue_name')
// Fixed via 20260816000000 RLS & trigger updates
⚠️ Direct Consequence: Required defensive null-checking and database trigger automation.
3
Global Theming & Visual Token Ripple Effects
The visual rebrand required migrating the primary color from navy (#002940) to teal (#123f5c) and converting all backgrounds from cream/beige (#faf8f5) to pure white (#ffffff).

Across 45+ screens, hardcoded color values and font weights became low-contrast or invisible against pure white backgrounds until every component was standardized with Montserrat design tokens.
// White text on white background regressions (69d8928)
// Unaligned button fonts and border opacity (7015d7d)
// Tab badge visibility fixes (ada7277, 02e13a3)
⚠️ Direct Consequence: Multi-pass design token audits and typography replacements.
4
Third-Party Cloud Integrations & Async Webhooks
The team connected 4 enterprise third-party platforms simultaneously: PayFast (payment gateway & ITN webhooks), Brevo (transactional email SMTP & Deno edge functions), HubSpot (blog API), and Google Places (address autocomplete).

External API rate limits, environment variable discrepancies between local/staging/Vercel, and webhook validation caused asynchronous failures if not guarded.
// PayFast ITN signature hash mismatch (d72a1c0)
// Brevo welcome email name resolution (942f3c9)
// Google Maps WebView vs Native SDK crashes (610412a)
⚠️ Direct Consequence: Deno edge functions with resilient fallback routines were deployed.
5
Native Android AAPT2 & ProGuard Build Toolchains
Updating the visual identity required replacing app icons, splash screens, and adaptive icons.

Android AAPT2 compilers strictly validate PNG file chunks (rejecting renamed JPEGs or non-square layers), while release APK ProGuard minification stripped Fresco/OkHttp network image handlers, causing blank cards in production APKs.
// Android AAPT2 build failures on malformed PNG (ca79028)
// Adaptive icon clipping outside safe zones (a27adba)
// Blank featured images in release APKs (608b61f)
⚠️ Direct Consequence: Custom ProGuard keep rules and automated asset converters.
6
High Scope Velocity Without Frozen Stabilization Windows
In June and July alone, over 78 commits were delivered with major structural changes. When features are added in rapid succession without a staging freeze, new features are built on top of newly merged features before the prior batch completes full end-to-end regression.

This high development velocity creates a temporary spike in defect density that naturally settles once features are frozen.
// June: 19 new features delivered in 30 days
// July: 24 desktop architecture commits delivered
// High velocity creates temporary error surface area
⚠️ Direct Consequence: Solved by enforcing automated Playwright E2E suites and staging gates.
